# Estimated tides — how they're generated

Every `programme-YYYY.csv` has two kinds of `High water` / `Tide height (m)` values, told apart by the `Tide source` column:

- **`Programme`** — printed on the club's programme itself. Taken as given, never touched by anything here.
- **`Estimated`** — not printed (coaching days, Friday RYA courses, cruise dates, the weekly Wednesdays that aren't in the club's main grid). Generated by the two scripts in this folder, marked with `≈` in the app.

This exists because the club's tide table is explicitly copyright-restricted to members (see `README.md`, "Adding a new season"), so the app can't pull a real table for the gaps. What's here instead is a lightweight approximation, openly documented as one, not a substitute for a proper harbour-authority table.

## Method

[Harmonic tidal analysis](https://en.wikipedia.org/wiki/Theory_of_tides#Harmonic_analysis): a real tide curve is well approximated by a handful of rotating components (*constituents*), each with a known, fixed astronomical frequency:

```
height(t) = Z0 + Σᵢ [ aᵢ·cos(speedᵢ·t) + bᵢ·sin(speedᵢ·t) ]
```

Because the speeds are fixed physical constants, this is **linear** in the unknowns (Z0, aᵢ, bᵢ) — solved directly with ordinary least squares, no iterative fitting, no starting guess to get wrong.

**Training data:** every `Programme`-sourced high water point in the season file being fitted from (113 points for 2026, spanning March–October).

**Constituents used — 5, not the full standard set:**

| | Name | Speed (°/hr) |
|---|---|---|
| M2 | principal lunar semi-diurnal | 28.9841042 |
| S2 | principal solar semi-diurnal | 30.0000000 |
| N2 | larger lunar elliptic semi-diurnal | 28.4397295 |
| K1 | lunisolar diurnal | 15.0410686 |
| O1 | principal lunar diurnal | 13.9430356 |

**Why only 5 — a real overfitting lesson, not a stylistic choice.** The first version of this script also included K2, P1, and M4. K2 sits within 0.08°/hr of S2, and P1 within 0.08°/hr of K1 — telling pairs that close apart needs a long, continuous, evenly-sampled water-level record, which is the normal input to a proper harmonic analysis. All we have is ~113 *isolated* daily high-water peaks, not a continuous curve. With 8 constituents, the fit still matched the 113 known points closely (RMS 0.059 m) — but away from those exact points, it swung to **heights over 10 m**, at a site with a real range of about 2.0–3.6 m. The design matrix's condition number tells the same story numerically: **1023** with 8 constituents, **41** with these 5. If anyone's tempted to add constituents back for "more accuracy," check the condition number and the full-year height envelope before trusting it — it's very easy to make the *training* fit look better while making every prediction between training points worse.

**Predicting a high water:** evaluate the fitted curve at 1-minute resolution across the target day, find every local peak (there are usually two), and return whichever is closest to a reference time (`--near`, default midday — the club's own high waters are always the daytime one).

## Accuracy

Three independent checks:

- **Held-out cross-validation** (fit on a random 80% of the 113 known points, tested on the other 20%, never used in fitting): height RMS **0.127 m**, max error **0.31 m**, mean bias **-0.004 m** (i.e. not systematically high or low).
- **Comparison against the 49 `Estimated` values already published** in `programme-2026.csv` (a check that this rebuilt version is consistent with what shipped, not a sanity check of the method itself, since those values came from an earlier, unrecorded run of essentially this same approach): time RMS **35 min**, max **63 min**; height RMS **0.23 m**, max **0.50 m**.
- **Run against all 162 dates in `programme-2026.csv` together** (both `Programme` and `Estimated` rows, read-only — nothing in that file was changed by this check):

  | | n | time RMS | time max | height RMS | height max |
  |---|---|---|---|---|---|
  | `Programme` (real, printed data) | 113 | 50 min | 144 min | 0.20 m | 0.50 m |
  | `Estimated` (already published) | 49 | 36 min | 63 min | 0.23 m | 0.50 m |

  **The real rows disagree *more* than the estimated ones — worth understanding why, not just noting.** `tidefit.py` fits by matching height at each point's *known* time, which it does well (RMS 0.108 m — see the fit's own output). But predicting a high water means asking the fitted curve "where's your peak?", a different question: a real tide's peak *timing* is shaped by things this model doesn't include — shallow-water distortion, the estuary's shape, weather — so even on days the model was trained on, its mathematical peak can land 20–50 minutes from when the tide actually turned. That's a more honest accuracy figure than the fit's own RMS, which only ever measured height at a known instant, never predicted timing — the thing that actually matters for a `≈ time` shown in the app.

Treat any single estimated value as good to roughly **±30–60 minutes** (occasionally more) and **±0.2–0.5 m** — adequate for "what's the tide doing around training/coaching today," not for anything requiring precision.

**Accuracy degrades outside the training window.** The fit only knows what it's shown. A date close to the programme's own covered dates (March–October) is on solid ground; a date well before or after that window (deep winter, for instance) is extrapolation and less trustworthy, even though the model will still confidently produce a number for it. This is exactly why `generate-tide-reference.py` (below) pools every season's file it can find, rather than just the latest — more real data, spread across more of the calendar, narrows this gap over time.

## Two ways to use this

**1. Bake estimates into a specific season's file**, once, when preparing it:

```bash
cd scripts/tide

# Refit against that season's printed programme dates
python3 tidefit.py ../../programme-2027.csv tide-model-2027.json

# Fill every blank tide row in that same file, in place — rows that
# already have a High water value (the real printed ones) are left
# completely untouched; only blanks get filled, and get Tide source
# set to "Estimated"
python3 tide_predict.py tide-model-2027.json --fill-csv ../../programme-2027.csv
```

Refit each season rather than reusing an old model — a new year's printed dates are the best available ground truth for that year, and refitting costs nothing. Check the printed `Height residual: RMS ...` line after step 1 is in a similar range to 2026's (around 0.1 m) — a much larger number suggests something about that year's data looks different and is worth a look before trusting the estimates it produces.

**2. A rolling reference for *any* date, kept current automatically.** `generate-tide-reference.py` pools every `programme-*.csv` present in the repo (so it only gets more accurate as more seasons accumulate), refits, and predicts a high water for every day in a rolling window — 24 months from today by default:

```bash
python3 generate-tide-reference.py --repo-root ../.. --months-ahead 24 --out ../../tides.json
```

This runs weekly via `.github/workflows/update-tides.yml`, the same pattern as the club events workflow — pushes straight to `main` using the same `RELEASE_TOKEN` secret (see README.md, "Club Events," for why that's needed and considered safe), and only actually commits when the *data* changed, not just the file's own timestamp. `tides.json` exists as a standalone, general-purpose dataset — **the app doesn't read it yet**; wiring it in as a fallback (so any date the app shows, not just a season's own pre-filled rows, can offer a tide) is a deliberate next step, not done here.

**Two genuine bugs were found and fixed while building the weekly refresh** — worth knowing about since the same mistakes are easy to make again if this is ever touched:

1. `git diff --quiet` only detects changes to a file git already knows about — it silently reports "no change" for a file that doesn't exist in the repo yet. `tides.json`'s very first run would have been skipped. Fixed by checking `git status --porcelain` instead, which correctly sees a brand-new file too.
2. Both `events.json` and `tides.json` carry their own `generated` timestamp, which changes every run regardless of whether the real content did — so a plain file diff always looks "changed," committing every single run for no reason. Fixed by comparing the JSON with that one field stripped out, in both workflows.

## Single-date lookups, for spot-checking

```bash
python3 tide_predict.py tide-model-2026.json 2026-11-20
python3 tide_predict.py tide-model-2026.json 2026-11-20 --near 14:00   # if midday isn't the expected peak
```
